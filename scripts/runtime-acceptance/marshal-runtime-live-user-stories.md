## 1. Purpose and acceptance rule

This document is the release acceptance contract for embedding `@marshal/runtime` in the Marshal Electron process. A capability is accepted only when its required evidence class is present:

| Evidence class      | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Acceptance weight                                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LIVE-ELECTRON`     | A real Electron main process and renderer are running. The embedded runtime, production adapters, IPC handlers, preload bridge, renderer, SessionManager, MemoryManager, permission policy, extension manager, kernel, UI controller, and filesystem paths are the application implementations from this worktree. `MARSHAL_E2E=1` may replace only external services such as the remote model backend; it must not replace or monkey-patch the Marshal Runtime host or any listed production adapter. Passive counters and fixture providers loaded through production registration paths are allowed. | Required whenever named by a story.                                                                                                                                                   |
| `LIVE-REAL-BACKEND` | `pnpm electron:debug` is connected through `e2e-real` CDP to a signed-in, non-stub backend.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Supplemental for ordinary-agent behavioral confidence; required only where a story says so.                                                                                           |
| `LIVE-PACKAGED`     | A shipping-equivalent unpacked or installed Electron artifact is running from `release\...`, loading runtime packages from `resources\app.asar.unpacked\node_modules`. The acceptance-only bridge is absent.                                                                                                                                                                                                                                                                                                                                                                                            | Conditional release evidence.                                                                                                                                                         |
| `NODE-INTEGRATION`  | A real Node process uses real runtime packages, OS processes, and real filesystem fixtures, but not Electron.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Supporting evidence for host-wired behavior; primary evidence only for public platform-package behavior that the document explicitly identifies as not wired into this Electron host. |
| `UNIT`              | Isolated Vitest coverage with doubles or in-memory state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Supporting evidence only.                                                                                                                                                             |
| `STATIC`            | File, export, archive, hash, or source inspection.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Supporting evidence only unless the capability is inherently absence/provenance proof.                                                                                                |

A passing unit or integration test must never be recorded as live Electron evidence. A screenshot without the corresponding API/IPC transcript is not sufficient. A successful API result without a live process identity and main-process log is not sufficient.

The extension loader's security boundary is trusted-root admission, package integrity, strict manifest validation, and dependency allowlisting. Extension code executes with `vm.Script.runInThisContext`; this specification makes no claim that an admitted extension is isolated from the host JavaScript global context.

## 2. Bug continuation policy

- **Blocking:** stop the dependent story chain, preserve all evidence, and file the failure before continuing. Independent stories may continue only if they cannot overwrite or conceal the failure.
- **Non-blocking:** capture the defect and continue. This classification is reserved for an explicitly optional environment or supplemental evidence; it does not turn a failed functional or security criterion into a pass.
- An environmental inability to produce `LIVE-PACKAGED` evidence is non-blocking for the source-process campaign, but the packaged story remains `NOT RUN` or `BLOCKED`, never `PASS`.

### 3.3 Acceptance-only bridge

The runtime API is intentionally not a renderer product API. Deterministic automation therefore requires a test-only bridge with these constraints:

- Compiled only when the build-time gate `MARSHAL_RUNTIME_ACCEPTANCE_BUILD=1` creates a non-shipping source acceptance build, and enabled only when `!app.isPackaged`, `MARSHAL_E2E=1`, and `MARSHAL_RUNTIME_ACCEPTANCE=1`.
- Named `window.runtimeAcceptanceAPI`.
- Registered through the typed `ipcHandle()` path and a separate acceptance preload module. The normal `electron\preload.cjs` must not expose it.
- Excluded from `electron-builder` inputs and shipping archives. Static inspection must prove that the bridge module, channels, preload property, and compile-time enable flag are absent from a normal packaged artifact.
- Calls the already-created `ProductionMarshalRuntimeApi`, `MarshalRuntimeHost`, `SessionManager`, and `MemoryManager`; it must not construct a parallel runtime host.
- Registers independently of runtime startup completion so `getStatus()` and `getStartupError()` remain available when the production host enters `failed`; it must not turn that failure into a synthetic running state.
- May observe production objects or configure existing production settings. It must not replace, monkey-patch, subclass, or proxy the runtime host, API, authority port, SessionManager, MemoryManager, extension manager, kernel, UI controller, IPC handlers, or renderer hook.
- Faults must be induced at an external boundary: finite extension fixtures loaded by the real extension manager, the permitted mock remote backend, filesystem permissions/mutations in disposable roots, or actual invalid requests. A test double installed in place of a listed production object invalidates `LIVE-ELECTRON` evidence.
- Returns JSON-serializable envelopes and emits a JSONL audit entry for every call, including start/end time, operation, scope, idempotency key, result code, receipts, and cancellation state. It must not record customer content.
- Accepts no arbitrary JavaScript, command, module path, output path, or package root from the renderer. Fixture creation uses an allowlisted profile enum plus bounded scalar options, always under the reported trusted root.
- Refuses to start unless all reported app-data, user-data, fixture, and evidence paths are beneath the isolated run roots. Session/memory observation is limited to acceptance-seeded identifiers and must not touch default user data.


`getBridgeInfo()` must report the compile-time gate, runtime gates, main-process PID, preload identity, and the instance IDs of the already-created host/API/controller references. `listRegisteredSelfTools()` and `invokeRegisteredSelfTool()` must use the exact `RuntimeTool` objects installed through `selfToolDeps.additionalTools`, not recreate their handlers. `setAcceptancePermission()` may change only the real production decision source used for runtime capability and `marshal.tool.invoke:*` permissions or resolve a real approval flow; it cannot override the fixed built-in permission table and must not install a permissive authority stub. `getInvocationCounts()` may report only passive diagnostics, fixture-provider counters, and permitted external-backend call logs.

`materializeExtensionFixture()` must create packages only under the live process's reported trusted extension root and return an opaque fixture ID, `packageRoot`, exact domain-separated SHA-256 integrity, identity, version, capability names, stable catalog IDs, resource URIs, and UI application IDs. `mutateExtensionFixture()` accepts only that opaque ID plus an allowlisted mutation enum. Fixtures must support activation delay/failure, disposal marker/failure, duplicate capability/resource/catalog, unsupported import, strict-manifest violations, path collisions, link/tree mutations, file/metadata limits, and UI application declarations.

For restart stories, the harness must preserve the same explicit user-data directory and the same E2E app-data root. Do not use the default per-test fixture cleanup until the final restart step completes.

## 9. Exit gate

The campaign is complete only when:

1. Every blocking story is `PASS`.
2. Every `LIVE-ELECTRON` story has a process identity, main-process log, raw API/IPC transcript, and story artifact.
3. Every platform-only `NODE-INTEGRATION` story records real process IDs, filesystem roots, and package/build identity; unit tests cannot substitute for it.
4. Source and packaged results are not conflated.
5. Restart stories reuse both the same explicit Electron user-data directory and the same Marshal app-data root, skip reseeding/cleanup between legs, and prove pre/post process identity.
6. No evidence was produced by mutating or cleaning either authoritative dirty worktree.
7. `MRT-LEG-001` proves the portable swarm subpath boundary, absence of activation exports and main-entry re-export, absence of host registration, and zero live default swarm capabilities.
8. `MRT-HAR-001` proves the acceptance bridge is absent from normal source and packaged production output; `MRT-HAR-002` proves it did not replace production objects.
9. The story set, completion ledger, stable-identifier registry, and traceability matrix pass structural consistency checks.
10. Every source-process result identifies the fresh build hashes produced from the run snapshot.

## 10. Known environmental prerequisites

- The compile-time-gated acceptance bridge/preload, reusable user-data plus app-data launcher, finite fixture package builder, passive diagnostics, Playwright output redirection, `e2e-real --results-dir`, and `99-marshal-runtime` suite specified above do not currently exist; they are prerequisites for automation and must remain non-shipping.
- The multi-process platform harnesses required by `MRT-PUI-001`, `MRT-PUI-002`, `MRT-PUI-005`, and cross-process integrity checks do not currently exist.
- Windows Developer Mode or elevated symlink privilege is needed for complete link/junction rejection evidence. Without it, the relevant security story remains `BLOCKED`.
- Port `9222` (source debug) and `9223` (packaged debug) must be free.
- Real-backend evidence requires a valid Marshal sign-in and may require interactive permission handling; deterministic `MARSHAL_E2E=1` evidence does not satisfy `LIVE-REAL-BACKEND`.
- Memory restart evidence for a non-default memory backend requires that backend to be configured. Local deterministic persistence may still validate wiring but must be labeled accordingly.
- Packaged evidence requires the repository's existing build prerequisites and enough disk space for Electron Builder; signing is not required for an unpacked local smoke unless release policy requires it.
- Process/window observation is required on Windows to prove `windowsHide:true`.
